# Formalization Status

This file separates Lean declarations present in source from protocol properties still awaiting formalization. A declaration is not described as kernel-checked until the pinned `lake build SIRM` succeeds for the relevant commit.

## Present in the repository

- Supply-state definition and initial-state invariant.
- Mint transition and invariant-preservation theorem.
- Burn transition with an explicit sufficient-outstanding precondition and invariant-preservation theorem.
- Exact 1.309% founder-rate representation as 13,090 ppm.
- Founder allocation floor formula, allocation upper-bound theorem, and founder-plus-remainder equality.
- Genesis allocation record with all non-founder pools explicitly unallocated.
- Generic finite-account, per-asset signed general-ledger model.
- Per-asset balance-conservation theorem for any journal entry carrying its balance proof.
- A balanced transfer-journal constructor for the signed general-ledger view.
- An injective holder-to-subledger mapping and a pointwise agreement relation for the designated ledger accounts.
- A theorem that a holder transfer and its matching per-asset journal preserve the subledger agreement and aggregate signed-ledger balance.
- Balanced holder-issuance and holder-burn journals using an explicitly unmapped counterpart account; their mapped subledger effects preserve pointwise holder/GL agreement, and each journal preserves aggregate signed-ledger balance.
- Per-asset holder holdings indexed by account and asset.
- A reconciliation invariant requiring nonnegative holder balances whose total equals outstanding supply.
- A theorem bounding each nonnegative holder balance by total holdings.
- A funded holder-transfer transition preserving balances, nonnegativity and supply reconciliation; self-transfer is a no-op.
- An issuance-to-holder transition that increases the holder balance and outstanding supply equally.
- A burn-from-holder transition bounded by that holder's balance, with a proof that this bound also protects aggregate outstanding supply.
- Proof-carrying transfer and holder-burn transitions: numeric preconditions are explicit proof arguments, so invalid requests have no admissible transition term; every resulting state preserves the holdings invariant.
- Generic reachable-state invariant theorem, instantiated by an authorization-gated holder state machine and a combined authorized financial machine. The combined machine updates holder balances and corresponding GL journals together; a stronger reachable-state theorem also preserves aggregate signed GL balance for every asset relative to the opening ledger.
- A dedicated `SIRMTests` Lake test-driver library covering a reconciled two-asset example, funded transfer, overspending rejection, self-transfer, issuance, holder burn, founder allocation arithmetic and journal conservation.
- `SIRM.TypedRegistry` defines distinct finite `AccountId` and `AssetId` types, total metadata registries, account classes and lifecycle statuses, asset decimal precision and issuer metadata, and a proof that each asset's issuer account shares its network. Registry-level issuance eligibility requires both an active asset and an active issuer.
- `SIRM.RegistryAwareFinancialMachine` wraps the existing authority/control policy with the typed registry's issuance gate. An issue step requires the existing policy plus an active asset and active issuer; transfer and burn policy predicates are unchanged. The wrapper reuses the combined holder/GL machine and its reachable-state conservation theorem.
- `SIRM.AssetUnits` defines explicit decimal-coefficient inputs, exact conversion to integer asset base units, rejection of nonrepresentable excess precision, and a range-bounded conversion returning `Fin (max + 1)` under a caller-supplied limit. No floating-point conversion or implicit rounding is introduced.
- `SIRM.AssetMigration` defines positive rational rates in target-base-units per source-base-unit, a proof-carrying quotient/remainder conversion, a cumulative dust state preserving the scaled-value equation, and cross-network route metadata. Dust state is indexed by the exact rate and an explicit accounting partition.
- `SIRM.AuthorizedAssetMigration` composes source burn and destination issue authorization with account-control and exact authority-grant checks, active endpoint/account checks, a route/source/recipient-indexed residual claim subledger, and one paired holder/GL state transition. Its verified machine preserves holder reconciliation, mapped subledger agreement, aggregate per-asset GL totals, and the residual scaled-value equation.
- `SIRM.ReplayProtectedAssetMigration` wraps the authorized migration with a migration-scoped expected-next-nonce function indexed by principal. A step requires exact nonce equality and returns the migration update plus a one-step nonce increment in the same state; stale and future nonce mismatches are rejected, and other principals' nonce values are unchanged.
- `SIRM.ReplayProtectedFinancialMachine` generalizes sequential replay protection to the complete authorized financial transition relation: transfer, issuance and burn share one per-principal nonce sequence, with the financial update and nonce increment paired atomically in the abstract state. Stale/future mismatch rejection, selected-principal increment, other-principal frame preservation, and reachable holder/GL conservation are proved.
- `SIRM.FinancialTransactionEnvelope` binds a typed transfer/issue/burn payload and request ID to an accepted response receipt. It proves receipt-first exact retry lookup and state non-interference, rejects rebinding an occupied ID to a different payload, proves a second request from the same principal cannot commit at an already-consumed nonce, rejects stale/future nonce as a new success, proves receipt key/payload/nonce consistency in every reachable state, and preserves the existing holder/GL conservation invariant. This is an abstract state-machine result, not a database linearizability or crash-durability proof.
- `SIRM.FinancialTransactionDenials` composes a denial-receipt cache with the success envelope using one request-ID namespace. It proves that authorization denials are admitted only at the exact current nonce and that authorized non-self transfers or burns with insufficient funds receive a distinct cached business-denial reason. Both denial classes store the exact request/reason/expected nonce, change neither balances nor GL nor nonce, and preserve the disjoint success/denial cache invariant over reachable processor states. Exact retry returns the original response without re-evaluating current authorization or funds. Self-transfers are excluded from insufficient-funds classification; issuance has no debit-funding precondition. The transition relation is parameterized by a fixed policy; policy mutation is not represented as a reachable in-machine transition. Expiry, signature, and other deterministic failure classes remain open.

- A finite static account-control relation, independent of authority grants, represented by principal/account pairs. The combined policy requires control of the source for transfers, the issuer for issuance, and the holder for burns, together with an exact grant. Issue grants bind both issuer and recipient; recipient control is not required by this model.
- A registry-backed authorization adapter and regression theorems for denial when control is absent, denial when the exact grant is absent, and an allowed Treasury-to-Alice issuance where Treasury controls the issuer account but not Alice's recipient account. The holder operation remains mint-to-recipient and does not debit the issuer.

- `SIRM.EscrowAccounting` defines a one-record authorized escrow lifecycle. Opening transfers funded, already-issued units from a depositor to a dedicated vault holder; release transfers the exact amount to the recorded beneficiary; cancellation returns it to the depositor. Separate ordinary-transfer and escrow-specific permissions are required. The verified machine preserves holder/supply reconciliation, mapped holder/GL agreement, aggregate signed GL totals, exact vault backing while pending, and terminal-state replay rejection.
- `SIRM.EscrowRegistry`, `SIRM.EscrowPooledReserve`, and `SIRM.EscrowFinancialIntegration` extend the primitive to concurrent escrow IDs, aggregate pending liabilities per asset, and one designated vault-holder inside `FinancialState`. The integrated machine proves exact equality between pending records, vault-holder balance, and its mapped GL subledger for every reachable state, in addition to the existing financial conservation invariants.
- `SIRM.EscrowTimeLocks` wraps the integrated multi-record escrow machine with a strictly monotone discrete `Nat` clock and an immutable per-ID deadline schedule. Opening, release and voluntary cancellation require the deadline to be in the future; after the deadline a separately authorized refund returns funds to the depositor and marks the record `expired`, not `cancelled`. The timed machine preserves the existing reachable holder/supply, vault-balance, pooled-liability and mapped-GL invariants. The clock is abstract: no wall-clock oracle, scheduler liveness, or persisted deadline field is proved.
- `SIRM.EscrowDisputes` adds a separately authorized dispute-intake transition. Only a depositor or beneficiary may be the claimant under the policy witness, and filing is restricted to a pending escrow strictly before its deadline. The filing is retained per ID; release, voluntary cancellation, and timeout expiry are blocked for that ID thereafter, while time may advance and other IDs remain operable. The reachable-state theorem preserves the existing timed financial/vault/pool/GL invariant. This is a permanent safety freeze only: adjudication, evidence authenticity, appeal, reversal, and external settlement finality are not proved.

## Not yet formalized

- Production migration execution: the repository proves a migration-scoped sequential nonce gate, but not a production transaction envelope, operation-wide nonce policy, idempotent response cache, external bridge settlement/finality, custody, rollback/failure execution, asset-collision handling, or production posting/valuation/backing of fractional residual claims. The model proves an authorized source burn paired with destination issuance, exact residual carry-forward and per-principal nonce increment in one abstract transition; it does not execute an external bridge or establish legal/economic backing.
- Proof that a static principal/account control entry corresponds to legal ownership, beneficial entitlement, or actual key possession; production identity enrollment and verification, lifecycle transition rules, key custody, signer thresholds, permission administration, and revocation remain open. Account classes and active/frozen/closed lifecycle labels are represented as descriptive metadata, but their legal meaning and transition policy are not established. The formal control relation is an asserted policy snapshot, not proof of real-world identity or title.
- Cryptographic signature validation, concrete role and threshold policy, freeze/closure rules, and permission-policy administration.
- A canonical finite account universe and concrete genesis assignment covering founder, treasury, validator, ecosystem, community and unallocated pools.
- Escrow dispute adjudication remains open: the current dispute layer freezes a disputed ID but does not validate evidence, choose a winner, settle to the beneficiary or depositor, allow appeals, or define reversal/finality policy.
- Production transaction execution remains open: canonical bytes/hash, signer/threshold verification (a v0 Ed25519 signed-request proposal with a Python reference and Rust implementation exists, without Lean statements; a sparse-Merkle state commitment proposal over balances, supply and nonces likewise), expiry, fees, deterministic event/error schemas, persisted nonce/receipt storage for remaining failure classes, rollback and crash recovery. `SIRM.ReplayProtectedFinancialMachine`, `SIRM.FinancialTransactionEnvelope`, and `SIRM.FinancialTransactionDenials` specify global nonce, typed success receipts, exact retries, and cached authorization/insufficient-funds denial receipts in Lean, but use unbounded `Nat`, exact typed-value equality, and abstract state transitions; they do not prove a concrete database, runtime serialization, crash durability, or Lean-to-Rust refinement.
- A complete production posting policy for custody, customer-liability, control, and other non-holder general-ledger accounts.
- Wall-clock binding for escrow deadlines and timeout scheduler liveness/automatic invocation; dispute adjudication, evidence authenticity/provenance, appeals, outcome-specific beneficiary/refund settlement, external settlement finality/evidence, reversals, credit lines and account restrictions. Discrete abstract deadline guards and the permissioned expiry refund are formalized; first-stage dispute intake/freeze is also formalized. Concurrent IDs, pooled obligations and vault/GL reconciliation remain covered by the integrated machine.
- Multi-asset FX, valuation and rounding-residual policies.
- Redemption obligations and their legal/operational preconditions.
- Reserve evidence and external attestations as explicit assumptions with freshness and provenance.
- Governance, validator-set changes, upgrades, rollback and recovery transitions.
- The correspondence between Lean definitions and Rust code. Differential tests of holdings-level Rust ports against independent Python references run in CI, but they are conformance evidence, not a refinement proof.
- Consensus safety, liveness, data availability and privacy proofs.

## Test execution

The pinned workflow explicitly invokes `lake build` and `lake test`. The test driver is a Lean library whose concrete theorem scenarios must compile; it is not a randomized runtime/fuzz harness. Linting is explicitly disabled until a linter driver is configured.

## Assurance rule

No theorem is described as proving more than its exact statement. The holder-supply invariant assumes that the account universe is complete and that each outstanding unit is assigned to exactly one holder/control account. It does not prove legal ownership, private-key custody or external reserves. A later implementation must have a refinement argument; ordinary tests alone do not establish full correspondence.

- The static account-control registry is a general finite many-to-many principal/account relation: a principal may control multiple accounts, and an account may be associated with multiple principals. The relation is a policy input and does not establish real-world ownership or key custody.


- `SIRM.FeeAccounting` defines an authorized fee transfer with explicit payer, beneficiary and fee-collector holder roles. The payer is debited gross base units, the beneficiary receives gross minus fee, and the collector receives the fee. Transfer permission and fee permission are separate witnesses. The combined two-leg journal is balanced and the verified machine preserves holder/supply reconciliation, mapped holder/GL agreement and aggregate signed GL totals. The initial model requires the collector to be in the holder universe; tariff calculation, non-holder revenue classification, production fee policy and runtime execution remain open.


The original single-record escrow primitive remains limited to one record and one dedicated vault holder, while later registry, pooled-reserve and financial-integration layers compose it for concurrent IDs and exact vault/GL backing. `EscrowTimeLocks` adds discrete deadline gating and an authorized `expired` terminal transition. `EscrowDisputes` composes over the timed machine and records a permanent per-ID filing that blocks release, voluntary cancellation and expiry for that ID, without blocking clock advancement or operations on other IDs. None of these abstract layers proves a wall-clock source, autonomous scheduler liveness, dispute adjudication, evidence authenticity, outcome settlement, external settlement finality, persisted idempotent responses or runtime atomicity.

## Canonical encoding (proposal v0)

- `SIRM.IntegratedPipeline` is a generic model of the integrated request pipeline (replay, conflict, stale and future nonce, deny-by-default authorization, cached denials that consume no nonce, accepted requests that advance only the sender's nonce by one, receipts never overwritten, invariants of accepted effects lifted to the whole pipeline). It is generic: no ledger, escrow or migration rule is modelled, so no balance invariant is proved, and it is not connected to the Rust or Python machines except by the shape of the pipeline.
- `SIRM.IntegratedLedger` instantiates that pipeline with a concrete shared-ledger core (all eleven operations: transfer, issue, burn, escrow open, release, cancel, expire, dispute, advance, migrate, resolve) and proves, for reachable states, conservation per asset (`minted = burned + sum of balances`), vault backing (vault balance = sum of pending escrows), well-formed escrow accounts and the migration equation (`source * num = target * den + dust`, `dust < den`). Natural-number amounts (no `u128` overflow modelling); dispute filings belong to pending records and freeze them, the clock never goes backwards and filings never change; not connected to the Rust or Python machines except by the shape of the operations. It also proves what authorization buys: deny by default, no debit of an account the sender does not control, time only by a clock grant, filings only by a dispute grant, supply only by an issue grant or the migration stream (62 theorems; the policy is a model of the Rust `authorized`, not connected to it). `SIRM.BoundedAmounts` adds the `u128` ceiling to this model as one more validation step (`boundVal`: a request whose effect would push a supply counter, a migration total or the migration amount past the ceiling is denied and changes nothing). Proved for any authorization and any validation that implies the preconditions: the ledger invariants still hold, and in every reachable state every supply counter, burned total, account balance, migration total and the carried remainder is at most `2^128 - 1` (balances and burned totals follow from conservation, so no separate balance check is needed for the bound). 13 theorems, only `propext` and `Quot.sound`, no Mathlib. The clock and the ids stay unbounded naturals, and nothing proves that the Rust or Python code checks exactly these conditions (differential evidence only). `SIRM.DisputeResolution` adds the smallest exit from a frozen dispute as a separate layer (proposal; the same operation is now also the eleventh operation `resolve` of the Lean pipeline, see below; not in the wire formats): `resolve` pays the escrow to the beneficiary or the depositor and consumes the filing, and `resolveStep` acts only with an explicit arbiter permission, on a pending escrow that has a filing. Proved (11 theorems, only `propext` and `Quot.sound`, no Mathlib): the ledger invariants are preserved, supply counters, migration totals and the clock are unchanged, the bounds of `SIRM.BoundedAmounts` are preserved, the payout is exactly the escrowed amount out of the vault, and an escrow cannot be resolved without the grant, without a filing, or twice. Who the arbiter is, evidence, deadlines, appeals and reversal stay open, and nothing claims a resolution is fair, only that it is accounted for. `resolve id toBen` is also an operation of `SIRM.IntegratedLedger` itself (precondition: the escrow is pending and has a filing; effect: the filing is consumed and the vault pays the beneficiary or the depositor), authorized by the explicit grant `ids p .resolve id`; all earlier invariants, the clock monotonicity, the bounds of `SIRM.BoundedAmounts` and the policy theorems were re-proved with it, and a new theorem `filing_removed_only_by_resolve_grant` states that a filing disappears only through a resolve by a principal holding that grant (`pipeline_files_stable` now excludes only a resolve of the same escrow). It matches the Rust and Python machines; there is still no wire encoding for it.
- `SIRM.AuthenticatedStep` wraps an arbitrary state machine with the signature-suite authorization: unauthorized requests leave the state unchanged, processed requests were authorized under the principal's registered suite, frozen or revoked accounts never reach the machine, and the machine's invariants carry over. It is generic and not yet instantiated with the integrated processor; the link between the signed message and the request is an assumption.
- `SIRM.ThresholdAuth` models k-of-n authorization as a plain list of independent signatures (no aggregation assumed): acceptance implies k distinct registered keys with verified signatures of permitted suites, zero thresholds and duplicate signatures never help. `SIRM.RecoveryDelay` models announce, wait, finalize and cancel for key recovery on top of `SIRM.KeyRegistry`: finalization before the delay is rejected, only the current key cancels, and the legacy-key rule is preserved. The verifier is abstract and the clock is a parameter; neither is proved here.
- `SIRM.KeyRegistry` models key lifecycle transitions (register, rotate, freeze, revoke, recover) as a state machine kept apart from the financial state. It proves that only the target principal's entry changes, that no successful transition replaces the post-quantum key of a bound account by a non-post-quantum key, that recovery and revocation need the recovery actor and credential, that frozen or revoked accounts are not authorized, and that key transitions leave any financial-state invariant intact. Thresholds, expiry, delays and linking to the processor are not modelled.
- `SIRM.SignatureSuite` is an abstract model of the proposed v1 authorization step: a suite registry carried by key records, a node policy and a total `authorize` function. It proves that acceptance uses the registered suite (no downgrade or substitution), that only policy-permitted suites authorize, and that a hybrid verifier needs both components. The signature verifier is an arbitrary parameter; no hardness or unforgeability of ML-DSA, SLH-DSA or Ed25519 is proved or assumed as an axiom, and it is not yet linked to the processor.
- `SIRM.CanonicalEncoding` and `SIRM.CanonicalRequestEncoding` formalize a fixed-width big-endian codec and a concrete bounded request layout with round-trip and injectivity theorems for in-range requests. This is a proposal checked against an executable Python reference (`scripts/canonical_encoding_reference.py`) and vectors in `engineering/canonical_encoding/results/vectors_v0.json`; it is not yet adopted as the protocol format. `SIRM.CanonicalRequestLink` maps `FinancialTransactionRequest` into that record through caller-supplied injective principal/holder/asset index maps and proves that two in-range requests with the same request ID and equal canonical encodings are equal; the index maps and their range bounds are assumptions, not constructed here. Chain id, signatures, expiry and state commitments remain open. A receipt/response encoding v0 proposal ([specification](engineering/canonical_encoding/SPEC_receipt_v0.md)) has an executable Python reference and a Rust codec checked against shared vectors; it has no Lean theorems and is not adopted.
- `SIRM.RequestEncodingV2` (17 theorems, only `propext` and `Quot.sound`, no Mathlib) models the byte layout of request encoding v2 (`engineering/canonical_encoding/SPEC_request_v2.md`, without the domain prefix) as one table from operation tag to field widths, covering all eleven operations including `resolve`. Proved: decoding the encoding of a valid request returns it (`decode_encode`), distinct valid requests have distinct encodings (`encode_injective`), every byte string the decoder accepts is the encoding of the request it returns and that request is valid, including the `resolve` side byte being 0 or 1 (`encode_decode`), and an unknown tag is rejected (`decode_unknown_tag`). Not proved: that the table agrees with the Rust and Python codecs (differential evidence in `request_v2_conformance.rs`), the domain prefix, the signature layer, the state commitment. Checked by SIRM.
- `SIRM.SignedEnvelopeV3` (11 theorems, only `propext` and `Quot.sound`, no Mathlib) models the byte layout of the signed request wire v3 on top of `SIRM.RequestEncodingV2`: `decodeEnv_encodeEnv`, `encodeEnv_injective`, `encodeEnv_decodeEnv` (every accepted wire is the canonical encoding of a valid envelope), rejection of any other domain (`decodeEnv_bad_domain`, the v2 wire domain, and the signing message itself, `sigMsg_not_a_wire`), and `sigMsg_injective` (the signing message fixes chain, suite, key id and the whole request). Not modelled: the signature, the key registry and the verification order; the suite table is hand-written, so its agreement with Rust and Python is differential evidence. Checked by SIRM.
- `SIRM.StateCommitmentV6` (10 theorems, only `propext` and `Quot.sound`, no Mathlib) states what the v6 root binds, with the hash abstract and its collision freedom a hypothesis: `payload_injective` and `root_binds` (equal roots have equal domain, shape, clock, migration totals and tree, config, cache and escrow digests), `v5_v6_roots_differ`, `cacheEntry_injective` and `cacheEntry_binds_fields` (the cache entry fixes the request, so the escrow id and the side of a cached `resolve`, and the stored outcome including cause 15). Not modelled: the sparse trees and the config, cache and escrow digests as functions of a machine state, list sorting, SHA-256 itself. Checked by SIRM.
- `SIRM.CacheDigestV6` (7 theorems, only `propext` and `Quot.sound`, no Mathlib) ties the cache digest to its content: a cache entry (request encoding v2 plus 11 outcome bytes) carries its own length through the operation tag at byte 44 (`cacheEntry_sd`), so the concatenation of entries determines the entry list (`flatten_injective`) and, under a collision-free hash, the digest determines the list of cached requests and outcomes (`cacheDigest_binds`). Not modelled: the machine sorting its entries by request id, building the list from its state, SHA-256. Checked by SIRM.
- `SIRM.EscrowConfigDigestV6` (26 theorems, only `propext` and `Quot.sound`, no Mathlib) does the same for the escrow digest (55-byte id entries: deadline, record, filing) and the config digest (shape, vault, deadlines, migration rate, controls, limits, ids with the arbiter grants as tag 10, clock): a count followed by fixed-width entries is unambiguous (`cp_inj`), an optional part is told apart by its flag byte (`encOpt_inj`), and under a collision-free hash `escrowDigest_binds` and `configDigest_binds` give that the digest determines everything it covers. Not modelled: building these lists from a machine state, sorting, SHA-256. Checked by SIRM.
