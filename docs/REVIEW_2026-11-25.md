# Review of 25 November 2026

**Reviewer:** Claude (Anthropic's AI model), the same system that wrote most of this code. This is a review by the
author-side tool, run on the committed sources of commit `70261f8` plus the tests added in the same change. It is
not a third-party audit. What was run, what was read and what was found is listed below with numbers, so that each
line can be repeated.

**Environment:** Rust 1.100.0 (conda-forge, 2026-11-09) with `cargo test --locked` and the committed `Cargo.lock`;
Python 3.12 with the `cryptography` package; RustSec advisory database commit `10db699` (2026-11-24). Locked
cryptographic dependencies: `ed25519-dalek` 2.2.0, `curve25519-dalek` 4.1.3, `sha2` 0.10.9.

## What was read

Read in full: `signed_v3.rs` (domain separation, chain id and key id in the signed message, length checks before every
slice, `verify_strict`, order of the checks). Read in part: `integrated.rs` (pipeline, validation, the balance
checks, `invariant`), `request_v2.rs` (decoder), `commit_v6.rs` (framing: one domain per component, fixed-width
fields, counts before lists, sorted entries, flag and zero fill for optional values), `machine.rs`. All 38 panic
sites outside test code were listed: 15 `expect` calls in the apply step and in `dispute.rs`, 21 `try_into().unwrap()`
on slices whose length is checked first, 2 `unreachable!`. The `expect` calls are exercised by the stress test; the
slice conversions of the decoders and verifiers by the random-input tests.

## Findings

| # | Kind | Finding | Disposition |
|---|---|---|---|
| F1 | information | The registry accepts weak (small-order) Ed25519 public keys, for example the identity point. Every signature under such a key is rejected by strict verification (tested). The specification asks for a point on the curve, not for a strong key. | No change. Rejecting weak keys at registration would be a stricter rule than the specification and the Python reference. |
| F2 | information | `Stored::token` computes `nonce + 1`. It cannot overflow through the machine (an accepted nonce is always below `u64::MAX`, by `nonce_class`); it would only for a hand-built `Accepted { nonce: u64::MAX }`. | No change. |
| F3 | design | The response cache has no bound: every distinct request id is kept, denials included, and denials consume no nonce. A registered principal can grow the memory of a node without limit. This follows from the rule that a denial is replayed, and the code base has no persistence or limit layer. | Open: a node needs a retention or rate-limit rule. |
| F4 | test gap, closed | No stress test of the machine against hostile input; no property test of the signature layer beyond the vectors and single-byte mutations; rejection of malformed keys was untested. | The tests listed above were added. |
| F5 | information | Unoptimised curve arithmetic made the signature tests slow. | `opt-level = 3` for the three cryptographic dependencies in the dev profile; the whole suite takes 52 seconds. |

No defect in the checked code was found in this review.

## Not covered

The other Rust modules (ledger, escrow, dispute, fees, migration, timelock, registry, receipt, commitments v0 to v5,
request v1, signed v0 to v2) were run by their tests and compared with the Python references, not read line by line;
the signed layers v0 to v2 are not stress-tested like v3. Side channels, constant-time behaviour and zeroisation were
not examined. `ed25519-dalek`, `curve25519-dalek` and `sha2` were checked against the advisory database only. ML-DSA
and the hybrid suite have no verifier, so only their refusal was checked. The Lean proofs were not re-read (the axioms of every theorem were scanned afterwards, see the follow-up below). Consensus, networking, persistence and
concurrency are not in the code base.

## Follow-up: axiom scan of the SIRM package

After the review, the axioms of every theorem of the Lean package were scanned (`scripts/axiom_scan.sh`; the Lean job of CI runs it as a step). Scanned: 1643 theorems (equation lemmas that exist in the compiled modules included) in 47 modules under `SIRM`. Result: none depends on an axiom other than `propext`, `Quot.sound` and `Classical.choice`; none depends on `sorryAx` or on an axiom added by `native_decide`; no module declares an axiom. 183 of them depend on `Classical.choice` (module and number of theorems, all 25 modules: `SIRM.Accounting` (8), `SIRM.Authorization` (3), `SIRM.AuthorizedAssetMigration` (7), `SIRM.AuthorizedFinancialMachine` (7), `SIRM.AuthorizedStateMachine` (3), `SIRM.CanonicalEncoding` (3), `SIRM.CanonicalRequestEncoding` (4), `SIRM.CanonicalRequestLink` (1), `SIRM.EscrowAccounting` (7), `SIRM.EscrowDisputes` (8), `SIRM.EscrowFinancialIntegration` (23), `SIRM.EscrowPooledReserve` (11), `SIRM.EscrowTimeLocks` (11), `SIRM.FeeAccounting` (12), `SIRM.FinancialCore` (4), `SIRM.FinancialTransactionDenials` (8), `SIRM.FinancialTransactionEnvelope` (11), `SIRM.HolderAccountingBridge` (18), `SIRM.Holdings` (13), `SIRM.IntegratedPipeline` (2), `SIRM.RegistryAwareFinancialMachine` (1), `SIRM.ReplayProtectedAssetMigration` (7), `SIRM.ReplayProtectedFinancialMachine` (7), `SIRM.ThresholdAuth` (3), `SIRM.TypedRegistry` (1)); that axiom is allowed, and counted so that it can be seen. The README states that `IntegratedLedger` and `BoundedAmounts` depend only on `propext` and `Quot.sound`; the same run confirms that no theorem of either depends on `Classical.choice`. The scanner was tested on a small module with a deliberate placeholder, a declared axiom and a `native_decide`: all three are reported and the exit code is non-zero; a use of `Classical.choice` is counted, not reported as a problem. The test is `scripts/axiom_scan_selftest.sh`; the Lean job of CI runs it as a step.

The scan also checked the claims of the documentation. The README and `docs/FORMALIZATION_STATUS.md` state that 12 modules depend only on `propext` and `Quot.sound`; `scripts/axiom_scan.sh` now fails if a theorem of any of them uses `Classical.choice`, and this run confirmed all of them. Two statements were wrong and are corrected: `SIRM.IntegratedPipeline` was documented as using only those two axioms (in `docs/INTEGRATED_STATE_MACHINE_PROPOSAL.md` and `docs/TESTING.md`), but 2 of its theorems depend on `Classical.choice`.
